# Auditoría de seguridad y cumplimiento — La Brasa (sistema de gestión de restaurante)

Fecha: 2026-09-22
Modo: **Auditoría completa** (no existe `docs/PLAN.md` ni `docs/LEGAL.md` ni `CLAUDE.md` en el repo; el análisis se basa únicamente en el código fuente, el historial de git y el README).

## Revisión — Auditoría completa

### Resumen

**Qué hace el proyecto**: sistema de gestión interno para un restaurante de parrilla ("La Brasa"). Permite a personal administrativo (un único rol, `Administrador`, autenticado con usuario/contraseña) gestionar mesas, meseros, productos del menú, pedidos (con sus líneas/`Contenido`) y turnos de caja. No hay registro de clientes finales, checkout, pagos en línea ni recolección de datos de consumidores: es una herramienta operativa de piso, no una tienda online.

**Stack real**: backend Node.js + Express 5, Prisma ORM 7 con `@prisma/adapter-pg` sobre PostgreSQL (Neon en producción según contexto del proyecto, no verificable desde el código); autenticación JWT propia (`jsonwebtoken` + `bcrypt`), sin OAuth ni verificación de email. Frontend React 19 + Vite + React Router 7, sin framework CSS. El backend está desplegado en Render (`https://restaurante-txbp.onrender.com`, ver `frontend/.env.production`).

**Datos personales encontrados** (ver inventario abajo): nombre de usuario y contraseña (hasheada) del `Administrador`, y nombre del `Mesero` (empleado). No se encontraron datos de clientes finales, datos sensibles en el sentido de la Ley 1581 (salud, origen étnico, biometría, etc.), ni datos de menores de edad.

**Normas que aplican (supuestos deducidos del código, sujetos a validación por un abogado)**:
- **Ley 1581 de 2012 (Habeas Data) y Decreto 1377 de 2013**: aplica de forma limitada porque el sistema trata datos personales de empleados (nombre de meseros, usuario del administrador). Al ser datos tratados en el marco de una relación laboral/contractual, es probable que no requieran autorización expresa del titular para su uso interno, pero sí exigen que el responsable (el restaurante) cumpla el **principio de seguridad** (medidas técnicas y administrativas razonables) y tenga, fuera del código, una política de tratamiento de datos y un procedimiento para atender derechos del titular (conocer, actualizar, rectificar, suprimir). El código no implementa ni documenta nada de esto (no hay aviso de privacidad, ni logs de consentimiento, ni endpoint para que un mesero solicite sus datos), lo cual es una brecha de cumplimiento, no de código.
- **Ley 1480 de 2011 (Estatuto del Consumidor) y Decreto 1074 de 2015 (antes Decreto 587 de 2016 para comercio electrónico)**: **no aplican en lo sustancial** porque no hay venta a consumidores finales a través de este sistema (no hay checkout de clientes, ni recolección de sus datos, ni procesamiento de pagos). Se deja constancia de este supuesto: si en el futuro se agrega un módulo de pedidos para clientes (ej. QR en mesa, pago en línea), esta conclusión debe revisarse.
- **Ley 2300 de 2023 (mensajes comerciales, "Ley Antitrámites"/regulación de spam)**: **no aplica**, no se encontró envío de SMS, WhatsApp o correos comerciales en el código.
- **Facturación electrónica DIAN**: el endpoint `POST /pedidos/:id/facturar` únicamente cambia el estado interno del pedido a `FACTURADO` y libera la mesa; **no genera una factura electrónica válida ante la DIAN** (no hay CUFE, resolución de facturación, ni integración con un proveedor tecnológico autorizado). Si el restaurante usa este sistema como único soporte de sus ventas para efectos tributarios, existe un **riesgo de incumplimiento de la normativa de facturación electrónica**, que debe validarse con el contador/abogado del negocio. El sistema parece ser una herramienta operativa complementaria, no el sistema de facturación fiscal.

**Veredicto**: **Con condiciones**. No se encontraron vulnerabilidades críticas de inyección, secretos filtrados en el historial de git, ni un panel administrativo sin autenticación. Sin embargo, hay varios hallazgos de severidad ALTA (CORS abierto, ausencia total de rate limiting en login, fugas sistemáticas de mensajes de error internos al cliente, ausencia de cabeceras de seguridad) que deben corregirse antes de considerar el proyecto listo para producción real o para mostrarlo como referencia de buenas prácticas de seguridad.

### Plan de corrección

1. **Sanear las respuestas de error en todos los controladores** (Hallazgo #3) — Esfuerzo: **M**. Crear un helper único que loggee el error completo en servidor y devuelva siempre un mensaje genérico al cliente; reemplazar los ~30 `catch` repetidos.
2. **Agregar rate limiting a `/admin/login`** (Hallazgo #1) — Esfuerzo: **S**. Instalar `express-rate-limit` y aplicarlo antes del handler de login.
3. **Restringir CORS a orígenes explícitos por entorno** (Hallazgo #2) — Esfuerzo: **S**. Definir una variable de entorno con el dominio del frontend y pasarla a `cors({ origin: [...] })`.
4. **Agregar `helmet()` y mover `prisma` a `devDependencies`** (Hallazgos #4 y #5) — Esfuerzo: **S**. Dos cambios pequeños e independientes en `backend/index.js` y `backend/package.json`.
5. **Migrar el token de `localStorage` a cookie `httpOnly`** (Hallazgo #6) — Esfuerzo: **L**. Requiere cambios coordinados en backend (emitir cookie, endpoint de logout, protección CSRF) y frontend (quitar el manejo manual de `Authorization`); dejarlo para un ciclo posterior si el tiempo es limitado, priorizando primero los puntos 1-4.

### Lo que está bien

- **Backend consistentemente parametrizado y sin asignación masiva**: cada controlador extrae y valida campos explícitos del `req.body` (nunca `data: req.body` directo), y todas las consultas pasan por Prisma sin `$queryRawUnsafe`. Esto elimina de raíz el riesgo de inyección SQL y de que un cliente cambie campos que no debería (ej. `role`).
- **Contraseñas bien manejadas**: uso correcto de `bcrypt.compare`, el hash nunca se devuelve al cliente, y el login no revela si el problema fue el usuario o la contraseña (`admin.controller.js:26-34`), evitando enumeración de usuarios.
- **Autorización real en el backend, no solo en el frontend**: el middleware `verificarToken` se aplica globalmente a todas las rutas salvo las dos explícitamente públicas (`backend/index.js:26-30`), así que aunque el frontend solo oculte rutas por conveniencia, el servidor sí decide.
